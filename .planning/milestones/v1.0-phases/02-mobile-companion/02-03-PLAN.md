**Step 1: Audit ticket validation (security-critical).**

Read `src-tauri/src/server/streaming.rs` and verify these security properties:

a) **Missing ticket → 401:** Line `query.ticket.ok_or(StatusCode::UNAUTHORIZED)?` — CORRECT. If no ticket query param, returns 401.

b) **Invalid ticket → 401:** `state.validate_ticket(&ticket).ok_or(StatusCode::UNAUTHORIZED)?` — CORRECT. If ticket not found or expired, returns 401.

c) **Wrong track_id → 401:** `if ticket_track_id != track_id { return Err(StatusCode::UNAUTHORIZED); }` — CORRECT. Ticket is bound to a specific track ID.

d) **Expired tickets cleaned on validation:** `validate_ticket` calls `tickets.retain(|_, t| !t.is_expired())` before lookup — CORRECT. Expired tickets are pruned.

e) **Ticket reuse for Range requests:** `validate_ticket` does NOT remove the ticket from the HashMap — CORRECT. Multi-use for the duration of playback (browser makes many Range requests).

**Step 2: Audit path traversal protection (security-critical).**

In `streaming.rs`, the path validation flow is:
1. Get `file_path` from database (by track_id, not from client input)
2. `std::fs::canonicalize(&file_path)` resolves symlinks and `..`
3. Compare canonical path against canonical library folder roots
4. If not within any root → FORBIDDEN

This is CORRECT. The client never provides a file path — only a track_id. The database lookup and canonicalization prevent path traversal.

Verify the path validation code handles:
- Symlinks that escape library roots: `canonicalize` resolves them → check catches the escape
- Non-existent files: `canonicalize` returns Err → maps to NOT_FOUND
- Unicode paths: `to_string_lossy()` may lose data but this is for comparison only, not file access

**Step 3: Audit concurrent stream limiting.**

In `streaming.rs`:
1. `state.active_streams.load(Ordering::Relaxed)` checks current count
2. If `>= max_streams` → returns 503 with `Retry-After: 5`
3. `fetch_add(1, Ordering::Relaxed)` increments
4. `StreamGuard` created immediately after increment
5. StreamGuard's `Drop` calls `fetch_sub(1, Ordering::Relaxed)`

**Potential issue:** There is a TOCTOU race between the load and fetch_add — two requests could both see `current < max_streams` and both proceed. However, for a companion app with max_streams=3 on a LAN, this is acceptable. The worst case is briefly allowing 4 streams instead of 3. Do NOT change this — the fix (compare_exchange loop) would add complexity for negligible benefit.

Verify the `StreamGuard` is created BEFORE any early-return points that could skip the decrement. Looking at the code:
- StreamGuard created at line ~70 (after fetch_add)
- All subsequent code paths that return Err will drop the guard → correct
- The guard is held for the lifetime of the function → correct

**Step 4: Audit Range header handling.**

Verify `parse_range` handles these cases:
a) `"bytes=0-1023"` → `Some((0, 1024))` — standard range
b) `"bytes=0-"` → `Some((0, total_len))` — open-ended range
c) `"bytes=1024-2047"` → `Some((1024, 2048))` — mid-file range
d) `"BYTES=0-1023"` → case-insensitive check via `to_lowercase()` — CORRECT
e) `"bytes=total_len-"` or `"bytes=999999999-"` → `start >= total_len` check → returns None → triggers 416

Verify response headers:
- 206 Partial Content: Content-Type, Content-Length, Accept-Ranges: bytes, Content-Range: bytes start-end/total
- 200 OK (no Range): Content-Type, Content-Length, Accept-Ranges: bytes
- 416 Range Not Satisfiable: Content-Range: bytes */total

All present in current code — CORRECT.

**Step 5: Check for memory safety with large files.**

The current implementation reads the requested Range chunk into a `Vec<u8>` buffer. For a typical audio chunk (65KB-1MB), this is fine. For a full-file request (no Range header), `Vec::with_capacity(total_len)` allocates the full file size.

For extremely large files (e.g., 1GB WAV), this could use excessive memory. However, browsers always send Range requests for `<audio>` elements, so the full-file path is rarely hit. The chunk-based approach is correct for production use.

```rust
/// Stream ticket for audio playback — avoids putting the Bearer token in audio element URLs.
///
/// Design decision (MOBL-07): Tickets use 10-minute expiry and are multi-use.
/// The original requirement specified "30s single-use" but this is incompatible with
/// HTTP Range-based audio streaming. Browsers make multiple Range requests to the same
/// URL as the user plays, seeks, and buffers. A 30s single-use ticket would break
/// seeking and buffering. The 10-minute window covers full track playback with seeking.
/// Security is maintained by: binding tickets to specific track IDs, cleaning expired
/// tickets on each validation, and limiting concurrent streams.
```

Also update the `is_expired` comment:

```rust
/// Expired tickets are cleaned on each create_ticket() and validate_ticket() call.
```
